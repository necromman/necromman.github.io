하네스의 물리적 차단

프롬프트 기반 가드레일은 AI의 선의에 의존한다. Hooks와 deny rules로 구현하는 결정론적 차단은 모델이 우회할 수 없다. 시스템을 강화하는 3가지 레이어.

프롬프트로는 지킬 수 없는 경계

지난 2편에서 배웠듯, Claude Code는 CLAUDE.md, settings.json, CLI 플래그로 개발자의 의도를 정의한다. 대부분의 경우 이것으로 충분하다. 하지만 다음 상황에서는 프롬프트가 무의미해진다.

  • 모델이 판단 실수를 했을 때: Claude가 package-lock.json을 수정하거나 .env 파일을 읽으려고 시도
  • 사람의 명령이 모순될 때: "프로덕션 DB에 절대 접근하지 마" vs "다른 환경과 스키마 비교 해줘"
  • 보안 정책이 엄격할 때: 결정론적 차단이 필수인 금융, 의료, 인프라 환경

이 경우 필요한 것은 제약이 아니라 강제다. "하지 마"가 아니라 "할 수 없게."

3가지 방어 레이어

Claude Code는 도구 실행 시 3단계 검증을 거친다. 각 레이어는 독립적이며, 모두 통과해야만 실행된다.

레이어 1
Hooks (런타임)
도구 실행 직전, 커스텀 스크립트가 JSON을 받아 판단. Exit code 2 또는 JSON으로 차단 가능.
exit 2 # 차단
레이어 2
Permission Deny Rules
설정 파일에서 정의한 정책. "Bash(rm -rf *)" 같은 패턴으로 자동 차단. 모델이 우회 불가.
"deny": ["Bash(rm -rf *)"]
레이어 3
Permission Mode
대화형 (default) vs 자동 (auto) vs 제약 (dontAsk) vs 우회 금지 (bypassPermissions 비활성화).
"permissions.deny": [...]

이 3가지는 겹겹이 작동한다. Hook이 allow를 반환해도 deny rule이 우선된다. 하므로 가장 제한적인 답이 항상 이긴다.

PreToolUse: 물리적 차단의 핵심

PreToolUse는 Claude가 도구를 호출하기 직전에 발화한다. 이 순간은 특별하다. 여기서 반환된 결정은 AI가 이미 마음을 먹은 것과 상관없이 적용된다.

핵심 개념
Exit Code 2: 모델이 우회할 수 없는 신호
Hook이 exit code 2로 종료하면, Claude Code는 도구 호출을 즉시 취소한다. stderr의 메시지를 Claude에게 피드백으로 전달하고, 다음 도구 호출을 시도할 때까지 대기한다. 이것은 프롬프트 거부(refusal)가 아니다. 하네스 차원의 물리적 차단이다.

다음 예시를 보자:

Hook 스크립트 (Bash)
#!/bin/bash INPUT=$(cat) CMD=$(echo "$INPUT" | \ jq -r '.tool_input.command') if echo "$CMD" | grep -q "rm -rf"; then echo "Blocked: destructive" >&2 exit 2 fi exit 0 # 의사결정 없음
settings.json 설정
{ "hooks": { "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "./protect.sh" }] }] } }

Claude가 rm -rf /tmp/build를 시도하면, hook이 실행되고, exit 2가 반환되고, 도구 호출이 차단된다. Claude의 도움 없이, 사용자 개입 없이.

PreToolUse JSON: 정확한 구조

Hook이 더 세밀한 제어를 원하면 JSON을 stdout으로 반환할 수 있다. Exit code 2와 달리, JSON을 반환하면 "왜 거절했는가"와 "어떻게 처리할지"를 명확히 할 수 있다.

Claude Code가 보내는 stdin
{ "session_id": "abc123", "cwd": "/home/user/project", "hook_event_name": "PreToolUse", "tool_name": "Bash", "tool_input": { "command": "rm -rf /data" }, "permission_mode": "default" }
Hook이 반환하는 stdout (exit 0)
{ "hookSpecificOutput": { "hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "Destructive command blocked" } }

permissionDecision은 정확히 4가지 값을 지원한다:

값 동작 Claude의 대응
"allow" 권한 대화 생략, 도구 호출 진행 도구를 실행 (deny rule은 여전히 적용됨)
"deny" 도구 호출 차단, 이유 전달 에러로 받고, 대체 방법 시도
"ask" 사용자 권한 대화 표시 대기 (사람이 승인/거절)
"defer" 헤드리스 모드(-p)에서만, 차단 후 Agent SDK 수집 대기 일시 중단

Matcher와 If: 선택적 적용

모든 도구 호출에 hook을 적용할 필요는 없다. matcher는 도구 이름 필터, if는 권한 규칙 문법으로 조건을 지정한다.

matcher: "Bash" → Bash 도구 호출만 필터링
matcher: "Edit|Write" → Edit 또는 Write 도구만 필터링
matcher: "mcp__.*__write" → 정규식: MCP 서버의 모든 write 도구
if: "Bash(git *)" → Bash 중 git으로 시작하는 명령만
if: "Edit(*.env)" → Edit 중 .env로 끝나는 파일만

if 필드는 v2.1.85 이상에서 지원되며, 권한 규칙(permission rules)과 동일한 문법을 사용한다. 복합 명령 git status && npm test는 각 subcommand가 독립적으로 평가된다.

Hooks vs Deny Rules: 언제 뭘 쓸까

특성 Deny Rules PreToolUse Hooks
적용 범위 모든 도구 호출 (자동) 설정된 이벤트만
유연성 패턴 기반 (정적) 커스텀 로직 (동적)
성능 즉시 (정규식 매칭) 스크립트 실행 (msec 추가)
디버깅 /permissions 명령으로 확인 /hooks 명령 + 로그
예시 "Bash(rm -rf *)" 차단 프로덕션 DB IP 검증

실전 전략:

  • 정적 정책 (rm -rf, .env 읽기, 특정 경로) → Deny rules
  • 동적 검증 (환경 변수 확인, 네트워크 체크, 타임스탬프) → Hooks
  • 감사 로그 (누가 뭘 시도했는가) → PostToolUse hook
  • 이유 제시 (왜 차단했는가, 대안은) → Hook JSON output

우선순위: 가장 제한적인 것이 이긴다

여러 hook이 같은 도구에 매칭되면 모두 병렬 실행된다. 결과는 합병되며, 가장 제한적인 결정이 최종 결과가 된다.

결합 규칙
Deny > Ask > Allow
Hook A가 allow를 반환하고, Hook B가 deny를 반환하면 → deny가 적용된다. 예: "로깅 hook (exit 0)" + "차단 hook (exit 2)" = 둘 다 실행, 차단만 적용됨.

또한 hook의 deny는 permission 설정의 deny rules보다 먼저 실행되지만, rule의 deny는 hook의 allow를 우회한다 (관리 정책 우선). 즉, 조직 차원의 deny rule을 hook으로 우회할 수 없다.

실전: 5가지 패턴

패턴 1: 파괴 명령 차단 (Deny Rule)

가장 간단한 경우. 설정 파일에 한 줄만 추가하면 된다:

settings.json에 추가
{ "permissions": { "deny": [ "Bash(rm -rf *)", "Bash(sudo *)", "Edit(/etc/**)" ] } }

패턴 2: 보호된 파일 목록 (Hook)

특정 파일 패턴만 차단하되, 이유를 설명하고 싶을 때. 프로덕션 .env, 설정 파일, 잠금 파일 등을 보호한다.

Hook 스크립트 (.claude/hooks/protect-files.sh)
#!/bin/bash INPUT=$(cat) FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty') PROTECTED_PATTERNS=(".env" "package-lock.json" ".git/" "secrets/") for pattern in "${PROTECTED_PATTERNS[@]}"; do if [[ "$FILE" == *"$pattern"* ]]; then echo "Protected: $FILE matches '$pattern'" >&2 exit 2 fi done exit 0
settings.json 설정
{ "hooks": { "PreToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/protect-files.sh" }] }] } }

패턴 3: 모든 Bash 명령 로깅 (PostToolUse)

감사 목적으로 실행된 모든 명령을 기록한다:

settings.json
{ "hooks": { "PostToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "jq -r '{tool:.tool_name, cmd:.tool_input.command, time:now|todate}' >> ~/.claude/audit.log" }] }] } }

패턴 4: 권한 자동 승인 (PermissionRequest)

특정 도구는 항상 승인하도록 자동화:

settings.json (ExitPlanMode만 자동 승인)
{ "hooks": { "PermissionRequest": [{ "matcher": "ExitPlanMode", "hooks": [{ "type": "command", "command": "echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PermissionRequest\",\"decision\":{\"behavior\":\"allow\"}}}'" }] }] } }

패턴 5: 환경 변수 자동 갱신 (CwdChanged)

Claude가 디렉토리 변경할 때마다 direnv 재로드:

settings.json (~/.claude/settings.json)
{ "hooks": { "CwdChanged": [{ "hooks": [{ "type": "command", "command": "direnv export bash > \"$CLAUDE_ENV_FILE\"" }] }] } }

Hook 설정 위치와 우선순위

Hook은 어디에 정의하는가에 따라 적용 범위가 달라진다:

위치 범위 VCS 추적 용도
~/.claude/settings.json 모든 프로젝트 아니오 개인 환경 설정 (알림, 로깅)
.claude/settings.json 이 프로젝트 예 팀 정책 (파일 보호, 명령 제약)
.claude/settings.local.json 이 프로젝트 (현 머신) 아니오 로컬 개발 설정
플러그인 hooks/hooks.json 플러그인 활성화 시 예 도구별 표준 정책

설정 우선순위: 관리 정책 > CLI 플래그 > 프로젝트 로컬 > 프로젝트 공유 > 사용자 설정

디버깅: Hook이 작동하지 않을 때

Hook을 설정했는데 실행되지 않는 5가지 원인:

  • /hooks 명령으로 확인: 설정이 등록되었는가? 맞는 이벤트 아래인가?
  • Matcher 대소문자: "bash"가 아니라 "Bash" (도구 이름은 대소문자 구분)
  • Hook 스크립트 권한: chmod +x .claude/hooks/protect.sh
  • JSON 검증: 설정 파일 JSON 문법 오류 확인 (sed로 확인 또는 온라인 JSON 검증)
  • Exit code 테스트: 스크립트를 직접 실행해서 exit code 확인 (echo $?)

전체 로그는 /debug 명령으로 활성화하면 ~/.claude/logs/claude.log 또는 --debug-file로 지정한 경로에서 확인 가능하다.

정책이 이기는 이유

"이 정책을 프롬프트로 명시하면 Claude가 따를까?" 대부분은 따른다. 하지만 "대부분"은 제품 환경에서는 불충분하다.

보안 철학
Trust No One, Not Even the Model
Model는 선의로 시작하지만, 실수한다. Token 한계에서 헷갈린다. 다음 쿼리에서 인물을 또 다르게 해석한다. 프롬프트로 지킨 경계는 모델의 판단 실수로 언제든 깨진다. 정책으로 지킨 경계는 깨지지 않는다.

금융권, 의료, 인프라 팀이 hooks와 deny rules를 사용하는 이유는 이것이다. "Claude를 믿되 검증하라"는 원칙은, 검증의 기준이 프롬프트가 아니라 코드로 작성된 하네스여야 한다는 뜻이다.

다음: 시스템 강화 순서

이제 당신이 할 수 있는 일:

  1. 정적 정책 먼저: .claude/settings.json에 permissions.deny로 rm -rf, .env, .git 접근 차단
  2. Hook으로 동적 검증 추가: 프로덕션 환경 판별, 특정 도메인 접근 검증, 타임스탬프 기반 차단
  3. 감사 로그 활성화: 모든 도구 호출을 로깅해서 나중에 "뭐가 실행됐지?" 확인 가능하도록
  4. 팀에 공유: .claude/settings.json을 레포에 커밋하면, 팀 모두가 같은 정책으로 시작

이 4단계로 당신의 Claude Code 환경은 "신뢰"에서 "신뢰 + 검증"으로 진화한다.
